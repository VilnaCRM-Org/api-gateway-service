## Executive Summary

`iam-service` is VilnaCRM's API gateway and central authorization service. It runs as two Kubernetes Deployments built from one image on AWS EKS: `iam-gateway`, the data plane behind an AWS Network Load Balancer, and `iam-control`, the control plane. For every client request the gateway terminates TLS, verifies the User service access token offline, authorizes the REST operation or every GraphQL field coordinate against an in-memory policy snapshot, and proxies the request to the upstream service. WebSocket, SSE and GraphQL subscriptions pass through the gateway as well: each operation is authorized when it opens, and open streams are re-evaluated and closed when policy or revocation state no longer allows them. Microservices that check their own actions call the same decision API on the gateway's decision listener (`GATEWAY_DECISION_LISTEN`, port 9091).

Permissions are not typed by hand. Each service uploads its OpenAPI and GraphQL contracts; IAM turns every REST operation and every GraphQL field into a permission key. Administrators group keys into roles and assign roles to users, globally or per project. Everything is denied unless a role grants it. Routes, upstreams and rate policies are IAM state too, managed through the same API.

IAM does not authenticate users; User service does. IAM validates User service's RS256 tokens offline and rejects tokens that live longer than 900 seconds. Session revocations reach IAM as User service events on Kafka, the common message bus; `iam-control` consumes them, records them in PostgreSQL and republishes them to every gateway pod. Operators can also revoke sessions and set token cut-offs through IAM's API. The token lifetime is the absolute backstop. Raw tokens are never stored or logged.

`iam-control` writes PostgreSQL, the system of record. Every policy change commits a gap-free policy version with one state record per changed entity, and a single fenced relay publishes those records to one ordered, compacted Kafka topic, `iam.policy.state.v1`. Each gateway pod reads the whole topic, checks version contiguity and a per-version digest, and applies each version to a copy-on-write snapshot. A pod allows a request only while its snapshot carries a freshness proof younger than `FRESHNESS_HARD_BOUND` (15 seconds now, 5 seconds as the target); otherwise it fails closed with 503. Revocation-class writes wait, by default, until every gateway pod has applied them (Sync-Fence). The gateway answers CORS preflights and refuses cross-site requests that ride on the session cookie, and calls between services go through the gateway's east-west listener, so upstreams trust principal headers only from gateway pods. The gateway's warm path has no PostgreSQL access, no Kafka producer and no remote call; Valkey is called only for routes that carry a rate policy and holds rate-limit counters only.

Change events leave on the Kafka topic `iam.events.v1`, which Notification service reads. A hash-chained security audit log in PostgreSQL records every administrative change. An access-decision log in Loki records every denial, every always-audit or sensitive-key decision and every wildcard allow in an acknowledged audit lane, and sampled allows in an ordinary lane; an always-audit or sensitive-key request whose record Loki cannot acknowledge is refused. Both logs are queryable through IAM's API.

Every IAM management capability is available over REST and over GraphQL with equivalent behaviour, served by the same command and query handlers. The service meets every bar of the Rust service template unchanged: 100% line and function coverage, zero surviving mutants, the complexity limits, the layer boundaries and the contract gates. The first release is sized and load-tested for a peak of 1,000 requests per second on a fleet set by zone availability. Every latency, capacity and propagation figure in this document is a target or an estimate until a benchmark story measures it.

Delivery: this bundle plans the whole product for issue #8 of `api-gateway-service`, a fresh copy of the Rust service template named "VilnaCRM API Gateway". ## Functional Requirements

### Interface parity and API conventions

**FR-1 REST and GraphQL parity.** Every IAM management capability listed in "API Surface Summary", including upstreams, routes, route configurations, rate policies, revocations, policy status, propagation wait, resync, bulk operations and access-log queries, is exposed both as a REST operation and as a GraphQL query or mutation, with the same inputs, outputs, validation rules, error semantics and side effects, dispatched to the same command or query handler through the template's command and query buses. The table in "API Surface Summary" is the authoritative pairing. No capability ships on one interface only. Traffic the gateway proxies to upstream services is not an IAM capability and is not covered by this rule.
Evidence: for every pair, an end-to-end scenario runs the same case over REST and GraphQL and asserts equivalent results (`make.e2e_tests`); both contract snapshots are regenerated and pinned by the contract-snapshot gate; the review gate fails any change that adds a capability on one interface only, and the API Surface Summary table is the checklist.

**FR-2 Administrative write conventions.** Every administrative create, update or delete:
- accepts an optional idempotency key (REST header `Idempotency-Key`, GraphQL input field `idempotencyKey`); a repeat with the same key and body within 24 hours returns the original result without a second change, and a repeat with a different body returns 422;
- for updates and deletes, requires the entity version (REST `If-Match` with the `ETag` returned on reads, GraphQL input field `expectedVersion`); a missing version returns 428 (GraphQL `PRECONDITION_REQUIRED`), and a stale version returns 412 (GraphQL `PRECONDITION_FAILED`);
- returns the new `policyVersion` (REST response header `Iam-Policy-Version` and body field, GraphQL payload field) whenever the change affects decisions;
- commits its policy state records (FR-70), its outbox event rows (FR-46) and its security audit record (FR-49) in the same database transaction as the change;
- accepts the write-mode modifier of FR-75 (REST header `Prefer: wait=propagated`, GraphQL input field `consistency: PUBLISHED | PROPAGATED`).
Creates return 201 with a `Location` header. Validation failures return 422 problem documents with violations; conflicts on unique names return 409.
Evidence: integration tests for replay, stale versions and transaction atomicity of state rows, event rows and the audit record (`make.integration_tests`); e2e scenarios over both interfaces (`make.e2e_tests`).

**FR-3 Authentication of IAM's own API.** Every IAM REST operation and every IAM GraphQL field requires a User service access token in `Authorization: Bearer <token>` or, when that header is absent, in the `__Host-auth_token` cookie (the gateway forwards the cookie only to `iam-control` and User service, FR-68, and refuses its cross-site use, FR-89), validated by the same pipeline as subject tokens (FR-15, FR-17). A service caller's token (`ROLE_SERVICE`) must also carry `JWT_CALLER_AUDIENCE` (default `vilnacrm-iam`) in `aud` and have a lifetime (`exp - iat`) of at most `JWT_SERVICE_TOKEN_MAX_LIFETIME` (default 900 seconds). A user caller's token is checked against revocation state through the `RevocationView` (FR-17); IAM makes no liveness call to User service. A missing, malformed, expired or revoked token, or a service token failing these rules, returns 401 with an `application/problem+json` body and a `WWW-Authenticate: Bearer` header (GraphQL: error with `extensions.code = UNAUTHENTICATED`). `/ping`, `/api/health`, the documentation routes and the template's example context are unaffected. The resolved identity is available to handlers and to GraphQL resolvers as context data. The OpenAPI document declares a `bearerAuth` security scheme on every IAM operation.
Evidence: e2e scenarios for each 401 cause over both interfaces; the Spectral gate passes with the security scheme; the OpenAPI breaking-change diff gate reports no breaking change for existing operations.

**FR-4 Authorization of IAM's own API.** IAM authorizes its own operations with its own model and enforces the rule twice: `iam-gateway` checks the operation's catalogue key from the policy snapshot before it forwards the request to `iam-control` (FR-59), and `iam-control` checks the full rule below from PostgreSQL. On startup, IAM's generated OpenAPI document and GraphQL SDL are registered as specifications of service `iam` (idempotent by content hash) and activated additively: a new IAM version is activated beside the older active IAM versions, and startup never orphans a grant. An older IAM version is retired only by an explicit, audited retirement that requires `iam:spec:iam`. Every IAM operation therefore has a catalogue key (`rest:iam:POST /api/roles`, `gql:iam:Mutation.createRole`). The rule for each operation is:
- validate access (single and batch) requires, per check, `iam:validate:{target service}` or `iam:validate:*` (FR-12); token resolution requires the reserved key of FR-12;
- revoking sessions and setting a user's cut-off require `iam:revoke:sessions`; setting the global cut-off requires `iam:revoke:global`;
- policy resync requires `iam:policy:resync`;
- creating or updating a route with `anonymous = true` or `enforcement = audit`, or changing either flag, requires `iam:route:anonymous`;
- creating, changing or deleting an upstream or a route whose catalogue service is S requires `iam:route:{S}` or `iam:route:*` at global scope (`RouteScopeGuard`); a route's `service` must equal its upstream's `catalogService` (422); upstreams and routes of service `iam` and every `system` entry are changed only by `iam-bootstrap`, and the API refuses them with 409 `system_entry`, audited;
- access-decision queries, security-audit queries, chain verification and revocation reads require `iam:audit:read`;
- every other IAM operation requires its catalogue key, plus the reserved keys of FR-25 (grants and assignments) and FR-30 (specifications) where they apply.
A request that fails its rule returns 403 with a problem document (GraphQL `extensions.code = FORBIDDEN`). A refusal by `iam-control` is recorded in the security audit log as a rejected attempt (FR-49); a refusal by the gateway is recorded as a denial in the access-decision log (FR-50). Reserved keys are exactly `iam:validate:{service}`, `iam:validate:*`, `iam:grant:{service}`, `iam:grant:*`, `iam:grant:sensitive`, `iam:grant:wildcard`, `iam:spec:{service}`, `iam:spec:*` (every service except `iam`), `iam:audit:read`, `iam:revoke:sessions`, `iam:revoke:global`, `iam:policy:resync`, `iam:route:anonymous`, `iam:route:{service}` and `iam:route:*` (every service except `iam`).
Evidence: e2e scenarios with a subject lacking each key, through the gateway and directly against `iam-control`; the audit log contains the rejected attempt; integration tests that startup registration is idempotent and that registering version 2, then version 1, then version 2 of IAM's own contract orphans no grant.

**FR-5 First-administrator bootstrap.** The CLI subcommand `service iam-bootstrap --admin-user <uuid>` (or `--admin-service <service-name>` for a service principal in automated environments; exactly one of the two) first registers IAM's own specifications through the path of FR-4, then creates the system role `iam-platform-admin` holding `rest:iam:*`, `gql:iam:*`, `iam:validate:*`, `iam:grant:*`, `iam:grant:sensitive`, `iam:grant:wildcard`, `iam:spec:*`, `iam:audit:read`, `iam:revoke:sessions`, `iam:revoke:global`, `iam:policy:resync`, `iam:route:anonymous` and `iam:route:*`, assigns it to the given subject at global scope, and writes an audit record with the operator actor `system:bootstrap`, all under a transaction-level advisory lock so that concurrent runs cannot create two administrators. With the optional `--iam-host <host>` the bootstrap also seeds, idempotently, the upstream `iam-control` (`forwardCredentials` true) and the routes that expose IAM's management API through the gateway on that host, as `system` entries that the API cannot change (409 `system_entry`, audited); without the option the seed is skipped and reported. `service iam-bootstrap --repair-routes --iam-host <host>` restores the seeded entries whether or not an administrator exists, under the same advisory lock, as an audited revocation-class change; without `--iam-host` it exits 2. It exits 0 on success, exits 1 without changes when an active assignment of `iam-platform-admin` already exists, and exits 2 on invalid input or configuration. System roles cannot be deleted or renamed through the API. A revocation, an expiry or an update that would leave no active, non-expiring global assignment of `iam-platform-admin` is refused with 409 and audited. The break-glass procedure (an audited re-run of the bootstrap with database access after the last administrator is lost) is documented in `docs/operations.md`.
Evidence: CLI integration tests for each exit code, for two concurrent runs, for repeated seeding that leaves one upstream and one route set, for a run without `--iam-host` and for the repair run (`make.integration_tests`); e2e scenarios in which a change to a seeded route is refused with 409; an e2e scenario in which the bootstrapped administrator creates a role through the gateway; e2e scenarios in which revoking or expiring the last administrator assignment is refused.

### Access validation

**FR-6 Validate access, single check.** REST `POST /api/access-validations` and GraphQL query `validateAccess(input)` accept:
- `credential` (required): the subject's access token as received by the caller;
- `service` (required): the target service name as registered in IAM;
- exactly one of `rest {method, path}`, `graphql {document, operationName?}` or `permissions [key, ...]`;
- `projectId` (optional UUID), `minPolicyVersion` (optional), `requestId` (required, echoed).
The response holds `decision` (`allow` or `deny`), `reason` (one of `allowed`, `token_missing`, `token_invalid`, `token_expired`, `token_revoked`, `unknown_service`, `unknown_operation`, `malformed_operation`, `permission_missing`, `scope_missing`, `limits_exceeded`, `unavailable`), `denied` (list of keys or coordinates), `scopes` (`all` or a list of project ids per allowed project-aware key), `subject {id, kind}`, `decisionId`, `policyVersion` and `requestId`. A valid request from an authorized caller always returns HTTP 200 with a decision body; non-200 statuses describe the caller's request only (401, 403, 413, 415, 422). The operation has no side effect other than metrics and the access-decision log. It is served by `iam-control` from PostgreSQL and by `iam-gateway` on its decision listener (`GATEWAY_DECISION_LISTEN`) from the policy snapshot, at the same paths, with a GraphQL endpoint there that exposes only the three decision queries (FR-6, FR-11, FR-19). Both planes give the same outcome for the same policy version. At the gateway, a snapshot without a valid freshness proof (FR-73) yields `deny` with reason `unavailable`. The reason `unavailable` never depends on User service.
Evidence: e2e scenarios for every reason code over both interfaces on both listeners, `unavailable` included through a stale snapshot at the gateway and a stopped database at `iam-control` (`make.e2e_tests`); the fault-injection integration suite (FR-13, NFR-15); Schemathesis against the published schema.

**FR-7 REST operation matching.** For `rest {method, path}`, IAM normalises the path (single leading slash, no trailing slash, no empty segments, query string ignored) and matches it against the operation templates of the target service's active OpenAPI versions, preferring literal segments over templated ones as OpenAPI specifies. A match yields the key `rest:{service}:{METHOD} {template}` with parameter names replaced by `{}`. Percent-encoding is decoded exactly once. A decoded path that still contains `%`, or contains `\`, a NUL, a `.` or `..` segment, an encoded `/` in the raw form, or more than 2,048 bytes, is rejected: `malformed_operation` in the decision API and 400 at the gateway. A path with no matching template is denied with `unknown_operation`; a service with no active OpenAPI version is denied with `unknown_service`. The gateway forwards the canonical re-encoded form of the decoded path, so the upstream's single decode yields exactly the bytes that were authorized.
Evidence: table-driven unit tests of normalisation and matching, including literal-over-template precedence and the residual-`%` rule (`make.unit_tests`); property tests that normalisation is idempotent and that re-encoding round-trips; e2e scenarios for each denial reason; the smuggling corpus of NFR-40.

**FR-8 GraphQL coordinate extraction.** For `graphql {document, operationName?}`, IAM parses the document, selects the operation (by name when several are present; a missing or unknown name is `malformed_operation`), resolves fragments and type conditions against the target service's active SDL versions and derives the set of required schema coordinates: root fields as `Query.x`, `Mutation.y` and `Subscription.z` (the `Subscription` root for subscription operations), and every selected field as `{Type}.{field}` (interface coordinates for selections outside a concrete fragment). `__typename` requires no permission; `__schema` and `__type` require `gql:{service}:__introspection`. Before resolution IAM enforces: document at most 64 KiB in the decision API (gateway body limits are FR-60), selection depth at most 15, at most 500 distinct coordinates, at most 50 aliases and at most 100 fragments; exceeding any limit yields `limits_exceeded`. A document that does not parse or does not validate against the SDL yields `malformed_operation`; a field unknown to every active version yields `unknown_operation`. Extracted coordinate sets are cached under a 128-bit hash of the document text plus the operation name and the catalogue version; every hit compares the full document text, so a hash collision can never change a decision. The decision is all-or-nothing, and `denied` lists every denied coordinate.
Evidence: unit tests over fragments, inline fragments, interfaces, aliases, subscriptions, introspection and each limit; a unit test in which two documents with a forced equal hash are told apart by the text comparison; e2e scenarios returning the denied list over both interfaces.

**FR-9 Permission-key checks.** For `permissions [key, ...]` (1 to 100 keys), each key must have the form `gql:{service}:...` or `rest:{service}:...` for the request's `service`, or be a reserved `iam:` key, and must exist in that service's active catalogue; otherwise the decision is `deny` with `unknown_operation` and the unknown keys in `denied`. Microservices use this form for their own internal actions.
Evidence: e2e scenarios with known, unknown and foreign-service keys.

**FR-10 Decision rule.** A check is allowed only when every required key is held by the subject in the requested scope, where held means:
- the subject has at least one assignment that is not expired (by the `Clock` port) whose role grants the key exactly, or grants one of the wildcards `gql:{service}:{Type}.*`, `gql:{service}:*`, `rest:{service}:{METHOD} *` or `rest:{service}:*` that covers it;
- wildcards never cover a key flagged sensitive (FR-30, FR-34);
- a global assignment applies to every project; a project assignment applies only when `projectId` equals its project; when `projectId` is absent, project assignments contribute their projects to `scopes` rather than allowing outright;
- orphaned (inactive) grants (FR-38) are ignored.
A subject without any assignment holding a required key is denied with `permission_missing`; a subject holding the key only in other projects is denied with `scope_missing`. The response's `scopes` lists `all` when a global assignment holds the key, or the project ids otherwise. The same `DecisionPolicy` runs in both planes.
Evidence: a maintained decision corpus executed as integration tests; property-based tests that adding a grant never turns an allow into a deny and that removing one never turns a deny into an allow.

**FR-11 Validate access, batch.** REST `POST /api/access-validations/batch` and GraphQL query `validateAccessBatch(inputs)` accept 1 to 100 checks of the FR-6 shape and return one result per check in request order, each with its own `decisionId`. Checks are evaluated independently; a malformed item produces a `deny` result with its reason without failing the others; each distinct credential is resolved once per batch. More than 100 checks returns 422. The operation is served on both listeners as FR-6.
Evidence: e2e scenarios with mixed allow, deny and malformed items over both interfaces on both listeners; an integration test asserting one token resolution per distinct credential.

**FR-12 Caller authorization for validation.** The caller is the identity of the bearer token on the request (FR-3), normally a `ROLE_SERVICE` principal; the subject is the identity of `credential`. A caller may validate checks for target service `s` only when it holds `iam:validate:s` or `iam:validate:*` (every item of a batch is checked; one refused item refuses the batch); otherwise IAM returns 403 and records the attempt in the security audit log. The caller needs no catalogue key for these operations. Token resolution (FR-19) requires `iam:validate:{caller's service name}` for a service caller, or `iam:validate:*` for any caller, which is how a user administrator holding `iam-platform-admin` resolves a token. A service caller's service name is the `sub` of its token (FR-15).
Evidence: e2e scenarios where one service asks about another service and is refused, and where a user administrator resolves a token.

**FR-13 Fail closed.** Any internal error during a decision yields `deny` with reason `unavailable` in the decision API, and 503 `iam_stale` (500 for a panic caught by the middleware) at the gateway's public listener; never `allow`. The causes include: a snapshot without a valid freshness proof (FR-73), an incomplete bootstrap, a digest or derived-state mismatch (FR-71, FR-74), and a PostgreSQL error or timeout in `iam-control`. There is no stale-grace window and no database fallback at the gateway.
Evidence: fault-injection integration tests for each cause, asserting denial at both planes (`make.integration_tests`); paused-time tests that an allow stops exactly when the proof is older than `FRESHNESS_HARD_BOUND`.

**FR-14 Read-your-writes.** At the gateway, a request carrying `X-IAM-Min-Policy-Version: V`, or the `__Host-iam_pv` cookie that the gateway sets on management write responses (`Max-Age` 60 seconds, `Secure`, `HttpOnly`, `SameSite=Strict`), waits up to `RYW_MAX_WAIT` (default 1 second) for a published snapshot of version V or higher. The barrier is checked before the snapshot is loaded and compares V with the published snapshot's version. A V above the highest version the pod has seen in the log, or a timeout, returns 503 `iam_propagating` with `Retry-After: 1`; the request is never decided on older state. In the decision API, `minPolicyVersion` gets the same wait on the gateway's decision listener; on `iam-control` a value above the current policy version returns 422, because policy versions are only ever issued by IAM.
Evidence: integration tests with paused time for the wait, the timeout and the immediate refusal of an unseen version (`make.integration_tests`); an e2e scenario in which a role revocation followed by a request carrying the returned version is denied through the gateway; an integration test that `minPolicyVersion` above the current version returns 422 at `iam-control`.

### Token validation and revocation

**FR-15 Offline token validation.** IAM accepts a credential only when it is a compact JWS signed with RS256 that verifies against one of the PEM public keys in `JWT_PUBLIC_KEYS_FILE` (1 to 3 keys, tried newest first, reloaded when the file changes), with `iss` equal to `JWT_ISSUER` (default `vilnacrm-user-service`), `aud` containing `JWT_AUDIENCE` (default `vilnacrm-api`), integer `exp`, `nbf` and `iat` checked through the `Clock` port within `JWT_CLOCK_SKEW` (default 30 seconds, maximum 60), a non-empty `sub` and `jti`, and `sid` whenever `roles` is present. A token with `exp - iat` above `MAX_TOKEN_LIFETIME` (default 900 seconds) is `token_invalid`. Tokens with any other algorithm (including `none` and every HMAC variant), with header parameters `jwk`, `jku`, `x5u` or `x5c`, or with a `crit` header are rejected. A `ROLE_SERVICE` token is accepted only when its `sub` matches the service-name pattern of FR-30; that `sub` is the service principal's service name. The outcome maps to `token_missing` (empty credential), `token_expired` (`exp` passed) or `token_invalid` (everything else). League OAuth2 tokens fail the issuer check (a deviation recorded in `research.md`). The resulting `AccessToken` value object carries the subject id, the subject kind (`user` for `ROLE_USER`, `service` for `ROLE_SERVICE`), the session id, the `jti`, the `iat`, the roles claim and the expiry.
Evidence: unit tests with tokens signed by a test key for every rejection rule, the lifetime rule and the skew bound with a controlled `Clock`; an integration test of key reload with three keys; an e2e scenario per reason code.

Epic 1 slice (FR-15): A benchmark in `crates/service/benches/` verifies RS256 JWS tokens with `jsonwebtoken` using its `aws_lc_rs` backend, against one trusted public key and against three trusted keys tried newest first, with RSA key pairs and tokens generated when the benchmark starts through `aws-lc-rs` (never the `rsa` crate). No private key or token is committed, no `openssl-sys` crate enters the dependency graph, and the dependency-policy gate passes with `jsonwebtoken` and `aws-lc-rs` as dev-dependencies of `crates/service` only.
Evidence: `make.bench_spikes` reports a median and a p99 per operation for one and three keys; `make.check_security` passes and the story records whether `aws-lc-rs` key generation passes the advisory check; `make.docs_check` passes with the bench sources free of committed keys and `docs/spikes/phase-0.md` listing the results (Story 1.6).

**FR-17 Token memo and revocation checks.** Each process keeps a memo of identities only (subject, kind, session, `iat`, `exp`, `jti`), never permissions, keyed by the SHA-256 digest of the credential, with a time to live of `min(exp - now, TOKEN_MEMO_MAX_TTL)` (default 900 seconds) and a capacity of `TOKEN_MEMO_CAPACITY` (default 200,000). Failed validations are memoised for 5 seconds in a separately bounded memo of at most 10,000 entries, so that a flood of random tokens cannot evict valid entries. On every request, memo hits included, the token is rejected with `token_revoked` when its session is revoked, when its `iat` is at or before the user's cut-off, or when its `iat` is at or before the global cut-off, read through the `RevocationView` port (the policy snapshot at the gateway, PostgreSQL in `iam-control`). The memo is flushed whenever the trusted key set changes.
Evidence: integration tests asserting one signature verification for repeated checks within the time to live, that a revocation recorded after memoisation takes effect on the next request, that the negative memo is bounded, and that a key-set change flushes the memo (`make.integration_tests`).

**FR-18 Revocation events from User service over Kafka.** When `USER_EVENTS_TOPIC` (`user.events.v1`) is set, `iam-control` consumes it with the consumer group `USER_EVENTS_CONSUMER_GROUP` (default `iam-control-user-events`) and applies:
- `user.session.revoked` {userId, sessionId}: the session is recorded as revoked;
- `user.all_sessions_revoked` and `user.refresh_token_theft_detected` {userId}: the user's cut-off (`tokens_valid_after`) is set so that every token whose `iat` is at or before the event's `occurredAt` plus `JWT_CLOCK_SKEW` is refused, because User service pods' clocks may differ (a user who signs in again within that margin is refused once);
- `user.deleted` {userId}: the cut-off is set and every assignment of the user is revoked with the actor `system:user-service`, audited and published as `iam.user_role.revoked`.
Each applied event commits a policy version with its revocation state records (FR-70) and an audit record, and emits `iam.session.revoked`, `iam.user_tokens.cut_off` or `iam.user_role.revoked`. The consumer is idempotent by event id through `iam_inbound_events` and commits the Kafka offset only after the PostgreSQL commit. An unknown event type is recorded as `ignored`; an undecodable record is recorded as `dead_letter`, counted and alerted; both are skipped, so one bad record never blocks the partition. The consumer accepts the neutral envelope `{id, type, occurredAt, data}` and the Symfony Messenger envelope (mapping the known `eventClass` values to these event names). Consumed revocations are fenced asynchronously (FR-76), so a slow gateway pod never stalls consumption. When the variable is unset, the consumer is not started.
Evidence: integration tests against the compose Kafka broker for each event type, both envelopes, duplicates, an unknown type, an undecodable record and a consumer stopped between the PostgreSQL commit and the offset commit (`make.integration_tests`); an e2e scenario in which a session revoked by an event is denied at the gateway.

Epic 1 slice (FR-18): Spike tests prove the two krafka capabilities the User service event consumer relies on: (a) consumer-group membership with manual commit after processing and rebalance handling, where records processed but not committed by a member that leaves are delivered again to the remaining member and no committed record is delivered twice; (b) SASL SCRAM-SHA-512 over TLS trusting a custom root CA generated at test time (no key committed), where the right credentials connect and a wrong password or an untrusted CA fail with distinguishable typed errors. The outcome of capabilities 8 and 9, and whether follower fetching (capability 12) is available, is recorded.
Evidence: integration tests in `crates/service/tests/integration/kafka_spike/` against the compose broker and its SASL_SSL listener (`make.integration_tests`); `docs/spikes/phase-0.md` records pass or fail per capability (`make.docs_check`) (Story 1.5).

**FR-19 Token resolution API.** REST `POST /api/token-resolutions` and GraphQL query `resolveToken(input)` accept `credential` and return the subject id, subject kind, session id, roles claim and expiry, or a 200 response with `resolved = false` and the token reason code. The raw credential is never echoed. The operation is served on both listeners as FR-6.

### Roles

**FR-20 Create role.** REST `POST /api/roles` and GraphQL mutation `createRole(input)` create a `Role` with `name` (1 to 100 characters, unique case-insensitively among non-deleted roles, no control characters) and optional `description` (at most 1,000 characters). The role starts with no grants and kind `custom`. The response carries the id, version, `ETag` and `Location`. A duplicate name returns 409. The event `iam.role.created` is recorded.
Evidence: e2e scenarios for success, validation failures and duplicates over both interfaces.

**FR-21 Read and list roles.** REST `GET /api/roles/{id}` and `GET /api/roles` (cursor pagination, page size 1 to 100, filter by name prefix and kind) and GraphQL `role(id)` and `roles(first, after, namePrefix, kind)` return roles with id, name, description, kind, grant count, version and timestamps. An unknown id returns 404 (GraphQL `null`).
Evidence: e2e scenarios over both interfaces; integration tests for pagination order and stability.

**FR-22 Update role.** REST `PATCH /api/roles/{id}` and GraphQL `updateRole(input)` change `name` and/or `description` under FR-2's version rules. System roles return 403. The event `iam.role.updated` is recorded.
Evidence: e2e scenarios for success, stale version and system role.

**FR-23 Delete role.** REST `DELETE /api/roles/{id}` and GraphQL `deleteRole(input)` delete a custom role and, in the same transaction, revoke every assignment of it, publish `iam.role.deleted` and one `iam.user_role.revoked` per revoked assignment, and commit a new policy version with its state records (FR-70). The response reports the number of revoked assignments. System roles return 403. The deletion is revocation-class: it runs in `propagated` mode by default (FR-75), in one transaction, or as one bulk operation when it changes more than `BULK_CHUNK_ENTITIES` entities (FR-84); former holders are denied on every gateway pod once the write, or the bulk operation's last fenced chunk, reports `complete` or `bounded`.
Evidence: an e2e scenario of delete followed by denial through the gateway; an integration test of atomicity; the Sync-Fence integration test of FR-76.

**FR-24 Role permission grants.** REST `GET /api/roles/{id}/permissions` and GraphQL field `Role.permissions` return the role's grants (key, kind `rest` or `gql`, service, active flag, wildcard flag). REST `PUT /api/roles/{id}/permissions` and GraphQL `setRolePermissions(input)` replace the full grant set (at most 5,000 keys) under FR-2's version rules. Each key must exist in an active catalogue or be one of the four wildcard forms of an existing service; unknown keys return 422 with one violation per key. Every added or removed key is subject to the escalation guards of FR-25; wildcards also require `iam:grant:wildcard` and are audited with `coversFutureElements = true`. The event `iam.role_permissions.changed` carries the added and removed keys. A replacement that removes at least one key is revocation-class and runs in `propagated` mode by default; a replacement that only adds keys uses `published` mode (FR-75).
Evidence: e2e scenarios for replacement, unknown keys, wildcard without the reserved key and stale version over both interfaces; e2e scenarios asserting the default write mode for a removal and for an addition.

**FR-25 Escalation guards.** The right to administer a permission is separate from the right to use it. An actor may grant or revoke a key of service `s` only when it holds `iam:grant:s` or `iam:grant:*` at global scope; a key flagged sensitive also requires `iam:grant:sensitive`, and a wildcard also requires `iam:grant:wildcard`. Reserved `iam:` keys belong to service `iam`. An actor may create, change or revoke an assignment of a role only when it holds those grant keys for every key the role grants. No actor may create, change or revoke an assignment whose subject is itself (same subject kind and id, for users and service principals alike). A violation returns 403 and is audited as a rejected attempt. The bootstrap command (FR-5) is the only way to create the first administrator.
Evidence: e2e scenarios for each guard, including one in which the bootstrapped administrator grants a key of another service, a sensitive one included, to a custom role.

The triple (subject, role, scope) is unique among active assignments; a duplicate returns 409. **FR-27 Read and list assignments.** REST `GET /api/user-roles/{id}` and `GET /api/user-roles` (filters `subjectKind`, `subjectId`, `roleId`, `projectId`, `includeExpired`; cursor pagination) and GraphQL `userRole(id)` and `userRoles(...)` return assignments with role name, scope, expiry, version and timestamps.

**FR-28 Update assignment.** REST `PATCH /api/user-roles/{id}` and GraphQL `updateUserRole(input)` change `expiresAt` (set, extend, shorten or clear) under FR-2's version rules. **FR-29 Revoke assignment.** REST `DELETE /api/user-roles/{id}` and GraphQL `revokeUserRole(input)` remove the assignment, commit a new policy version with its state records (FR-70) and record `iam.user_role.revoked`. Revoking the last active global assignment of `iam-platform-admin` returns 409 (FR-5). ### GraphQL specifications and permissions

**FR-30 Load GraphQL specification (`LoadGraphQlSpec`).** REST `POST /api/graphql-specs` and GraphQL `loadGraphqlSpec(input)` accept `service` (matching `^[a-z][a-z0-9]*(-[a-z0-9]+)*$`, at most 63 characters) and `sdl` (at most 5 MiB). IAM parses and validates the SDL, rejects documents with more than 10,000 types or 100,000 fields, records field directives `@iamSensitive` and `@iamAuditAlways`, and stores an immutable `GraphQlSpec` version in status `draft` with its SHA-256 content hash and its coordinate set. Uploading content identical to an existing version of the same service returns 200 with that version; a new version returns 201. Invalid SDL returns 422 with the parser's line and column. The response includes the diff against the active versions (FR-31). The event `iam.graphql_spec.loaded` is recorded. Loading, activating (FR-32, FR-36) and retiring (FR-38) a specification of service `s` require, besides the operation key, `iam:spec:s` or `iam:spec:*`, checked against the `service` of the request or of the stored version. The service name `iam` is reserved: only IAM's startup registration (actor `system:startup`) loads or activates its versions, any other request for it returns 403, and `iam:spec:*` does not cover it. Delivery pipelines are service principals holding `iam:spec:{their service}` through an assigned role. (Uploads through the gateway use the 6 MiB route limit of FR-60.)
Evidence: e2e scenarios for new, identical and invalid uploads over both interfaces, for an upload for another service refused with 403, and for an upload for service `iam` refused; unit tests of SDL limits.

**FR-31 Read GraphQL specifications and diffs.** REST `GET /api/graphql-specs` (filters `service`, `status`), `GET /api/graphql-specs/{id}` and `GET /api/graphql-specs/{id}/diff`, and GraphQL `graphqlSpecs(...)`, `graphqlSpec(id)` and field `GraphQlSpec.diff`, return version metadata (service, hash, status, uploader, timestamps, coordinate count), optionally the SDL, and the diff against the currently active versions: added coordinates, removed coordinates, removed coordinates that have grants (with the affected roles), wildcard grants that would gain access to added coordinates, and flag downgrades (coordinates that would lose the sensitive or always-audit flag in the union of active versions).
Evidence: e2e scenarios with a version that removes a granted field and with a version that drops a sensitive flag.

**FR-32 Create GraphQL permissions (`CreateGraphQlPermissions`).** REST `POST /api/graphql-specs/{id}/permissions` and GraphQL `createGraphqlPermissions(input)` activate a draft version: in one transaction they create a `GraphQlPermission` (key `gql:{service}:{Type}.{field}`, plus the root-field keys and `gql:{service}:__introspection`) for every coordinate not yet in the catalogue, update the sensitive and always-audit flags, mark the version `active`, apply FR-38 to coordinates no active version contains any more, and commit a new policy version and catalogue epoch with their state records (FR-70). Several versions of one service may be active at once; the catalogue is their union, and each key's flags are the most restrictive across the active versions (sensitive or always-audit if any active version says so). When the activation would orphan grants, the request must carry `confirmOrphans = true`, else it returns 409 listing the grants. When it would downgrade a flag, the request must carry `confirmFlagDowngrade = true` and the actor must hold `iam:grant:sensitive`, else it returns 409 (GraphQL `FLAG_DOWNGRADE_CONFIRMATION_REQUIRED`) listing the keys, or 403 without the reserved key. Optional `renames` (old coordinate to new coordinate) migrate grants and are audited. Activation of an already active version is a no-op returning 200. The event `iam.graphql_permissions.created` is recorded with `createdKeys`, `renamed` and `flagChanges` (each key with its old and new sensitive and always-audit flags), and `iam.permissions.orphaned` when grants were orphaned. An activation that orphans grants is revocation-class (FR-75).
Evidence: e2e scenarios for activation, orphan confirmation, flag-downgrade confirmation and rename over both interfaces; an integration test that a check against a newly activated field is evaluated against the new catalogue.

**FR-33 Get GraphQL permissions (`GetGraphQlPermissions`).** REST `GET /api/graphql-permissions` (filters `service`, `type`, `active`, `sensitive`, key prefix; cursor pagination) and `GET /api/graphql-permissions/{id}`, and GraphQL `graphqlPermissions(...)` and `graphqlPermission(id)`, return permissions with key, service, type, field, flags, active state, the versions that contain them and the roles that grant them.
Evidence: e2e scenarios over both interfaces.

### OpenAPI specifications and REST permissions

**FR-34 Load OpenAPI specification (`LoadOpenApiSpec`).** REST `POST /api/openapi-specs` and GraphQL `loadOpenapiSpec(input)` accept `service` (as FR-30) and `document`, an OpenAPI 3.0.x or 3.1.x JSON document of at most 5 MiB. IAM resolves only internal `#/` references and rejects any external reference, rejects documents with more than 5,000 operations or two operations that normalise to the same key, records `x-iam-sensitive: true` and `x-iam-audit: always` on operations, and stores an immutable `OpenApiSpec` version in status `draft` with its content hash and its operation set (method, normalised template, `operationId` as label). Identical content returns 200 with the existing version; a new version returns 201; invalid documents return 422 with the JSON pointer of the fault. The response includes the diff (FR-35). The event `iam.openapi_spec.loaded` is recorded. The `iam:spec` rule and the reserved service name `iam` of FR-30 apply.

**FR-35 Read OpenAPI specifications and diffs.** REST `GET /api/openapi-specs`, `GET /api/openapi-specs/{id}` and `GET /api/openapi-specs/{id}/diff`, and GraphQL `openapiSpecs(...)`, `openapiSpec(id)` and field `OpenApiSpec.diff`, behave as FR-31 for operations.
Evidence: e2e scenarios over both interfaces.

**FR-36 Create REST permissions (`CreateRestPermissions`).** REST `POST /api/openapi-specs/{id}/permissions` and GraphQL `createRestPermissions(input)` activate an OpenAPI version exactly as FR-32 does for GraphQL, creating `RestPermission` entries with keys `rest:{service}:{METHOD} {template}`, with the same orphan and flag-downgrade confirmation, most-restrictive flags, renames, multiple active versions, policy version and catalogue epoch with state records, and events (`iam.rest_permissions.created` with `createdKeys`, `renamed` and `flagChanges`, and `iam.permissions.orphaned`). An activation that orphans grants is revocation-class (FR-75).
Evidence: e2e scenarios over both interfaces; an integration test that FR-7 matching uses the activated templates.

**FR-37 Get REST permissions (`GetRestPermissions`).** REST `GET /api/rest-permissions` (filters `service`, `method`, `active`, `sensitive`, template prefix) and `GET /api/rest-permissions/{id}`, and GraphQL `restPermissions(...)` and `restPermission(id)`, behave as FR-33 for REST permissions.

**FR-38 Orphaned grants, retirement and purge.** A grant whose key no active version of its service contains is marked inactive (orphaned), ignored by decisions, kept for `ORPHANED_GRANT_RETENTION` (default 90 days) and then purged by the maintenance task (FR-43) with an audit record. A key that reappears in a later activation does not reactivate its orphaned grants; an administrator re-grants explicitly. REST `POST /api/graphql-specs/{id}/retirement` and `POST /api/openapi-specs/{id}/retirement`, and GraphQL `retireGraphqlSpec(input)` and `retireOpenapiSpec(input)`, retire an active version under the same orphan-confirmation and flag-downgrade rules and the `iam:spec` rule of FR-30, and record `iam.graphql_spec.retired` or `iam.openapi_spec.retired`. A retirement that orphans grants is revocation-class (FR-75).
Evidence: integration tests of orphaning, non-reactivation and purge with a controlled `Clock`; e2e scenarios for retirement over both interfaces.

### Effective permissions

**FR-39 Effective permission read model (`UserRolePermission`).** REST `GET /api/users/{userId}/role-permissions` (optional `projectId`, `service`) and GraphQL `userRolePermissions(userId, projectId, service)` return the subject's effective permissions: each held key or wildcard with the granting roles, the scopes (`all` or project ids), expiry of the shortest-lived contributing assignment, and the `policyVersion` the answer reflects. The answer is computed by `iam-control` from PostgreSQL with the same composition the decision rule uses (compiled per-role sets united over the subject's active assignments), so that for every key the read model and FR-10 agree. This read model covers user subjects; the roles of a service principal are listed through FR-27 with `subjectKind = service`.
Evidence: e2e scenarios over both interfaces; a property test that for random policies the read model's key set equals the set of keys FR-10 allows.

### Background tasks and maintenance

**FR-43 Maintenance task.** A singleton task in `iam-control` (FR-45) runs every `MAINTENANCE_INTERVAL` (default 10 minutes). It purges orphaned grants past `ORPHANED_GRANT_RETENTION` (FR-38), expired idempotency records and change receipts, and inbound-event ids older than 7 days, and it publishes the current audit chain head as `iam.security_audit.anchored` (FR-52). It reconciles no cache: divergence detection is FR-77 and revocation pruning is FR-79.
Evidence: integration tests with a controlled `Clock` that each purge happens after its retention and not before, and that each run publishes one anchor event (`make.integration_tests`).

**FR-45 Background task hosting.** `service serve` (`iam-control`) runs the outbox relay, the User service event consumer, anti-entropy, the revocation-tombstone emitter, maintenance, the bulk-operation runner, the Sync-Fence coordinator and the rejected-attempt writer. Every batch of a singleton task runs in a transaction that first takes the task's transaction-level PostgreSQL advisory lock (`pg_try_advisory_xact_lock`); a replica that does not get the lock skips that batch and tries again at the task's next interval, at most 10 seconds later, so leadership is fenced per batch and moves as soon as a holder stops. `service gateway` (`iam-gateway`) runs the policy tail, the freshness probe, the apply thread with the derived-state check, the EndpointSlice watch, the peer readiness checks and the access-log writer. Every loop is a pure step function with a shell that has no branching (NFR-2). There is no `service worker` mode. On SIGTERM or SIGINT, tasks stop accepting new work, flush in-flight batches and commit or roll back their transactions within `SHUTDOWN_GRACE_PERIOD`.
Evidence: integration tests that two instances never run a batch of the same singleton concurrently, including after the lock holder's connection is terminated, that leadership moves when the holder stops, and that shutdown completes within the grace period for both modes.

### Change events and notifications

**FR-46 Transactional outbox and Kafka relay.** Every state record and every change event is written to the outbox table `iam_outbox` in the same transaction as the change. The `OutboxRelay` singleton publishes state rows to `POLICY_TOPIC` (`iam.policy.state.v1`) on partition 0 explicitly and event rows to `EVENTS_TOPIC` (`iam.events.v1`), with `acks=all`, idempotent producing, at most one request in flight and lz4 compression. It uses the transactional producer `iam-relay` when phase-0 spike story 1.4 confirms support, with `KAFKA_TRANSACTION_TIMEOUT` (`transaction.timeout.ms`, default 10 seconds) below `FRESHNESS_HARD_BOUND`; in that mode a row counts as published, and its offset is stored, only once its transaction has committed, and rows of an aborted transaction are sent again. Otherwise it uses the relay-epoch header (`iam-relay-epoch`) taken from a PostgreSQL counter incremented on every relay takeover. It wakes on PostgreSQL `LISTEN` with a 100 ms poll fallback (CONFIG), stores the offset Kafka returns for each row, marks rows published, refuses to publish when the state topic has more than one partition, and deletes published rows after 7 days.
Evidence: integration tests against the compose Kafka broker for publication, ordering on partition 0, offsets stored, no loss when the relay stops mid-batch, refusal on a second partition, and fencing of a second relay (`make.integration_tests`).

Epic 1 slice (FR-46): Spike tests prove the producer capabilities the relay relies on: (a) an idempotent producer with `acks=all`, at most one request in flight, explicit partition 0 and lz4 compression writes 10,000 records under injected retriable errors exactly once, in order and with contiguous offsets; (b) a transactional producer with `transactional.id` `iam-relay` is fenced when a second producer with the same id initialises, and none of its records becomes visible to a `read_committed` reader; (c) aborted transactions are invisible to a `read_committed` reader; (d) `ListOffsets` with isolation `READ_COMMITTED` stops at the last stable offset while a transaction is open, and the broker aborts a transaction whose producer stops within a 10-second `transaction.timeout.ms`. The outcome of capabilities 6 and 7 is recorded.
Evidence: integration tests against the compose broker and krafka's `test-broker` (`make.integration_tests`); `docs/spikes/phase-0.md` records pass or fail (`make.docs_check`) (Story 1.4).

**FR-47 Event catalogue and envelope.** Messages use the envelope `{id (UUID v7), type, occurredAt (RFC 3339 UTC), data}` with `type` matching `^[a-z][a-z0-9]*([._-][a-z0-9]+)*$` and a total size of at most 64 KiB, compatible with Notification service's envelope. The Kafka record key is the aggregate id and the value is the envelope. The catalogue is listed in "Event Catalogue"; `data` always carries the aggregate id, the entity version, the actor (subject reference or `system:<component>`) and the resulting `policyVersion`, never a token or a specification document.
Evidence: unit tests of the envelope schema and size bound; integration tests asserting the published key and body of each event type.

**FR-48 Notification events.** The events intended for Notification service are `iam.user_role.assigned`, `iam.user_role.revoked` (`data` includes `subject {kind, id}`, `userId` when the subject is a user, `roleId`, `roleName`, `scope`, actor), `iam.privileged_role.assigned` (additionally `privilegedKeys`) and `iam.permissions.orphaned` (`service`, specification version id, orphaned keys, affected role ids). They are published on `iam.events.v1` with every other change event; Notification service tails that topic and selects them by `type`. IAM writes into no topic of Notification service.
Evidence: e2e scenarios asserting that each notification event appears on `iam.events.v1` in the compose broker with the documented fields.

### Security and access logs

**FR-49 Security audit log, write.** Every committed administrative change and every rejected administrative attempt (401 on an IAM route excluded, 403 included) is recorded as a `SecurityAuditEvent` with timestamp, event id, actor, the caller service when different from the actor, action, target type and id, scope, before and after values (identifiers, role names and permission keys only, never a person's name or email, a token or a specification body), idempotency key, outcome, optional `reason`, resulting `policyVersion`, request id and the SHA-256 hash of the previous record concatenated with this record's canonical form. Records of committed changes are written in the change's transaction under the chain-head lock. Rejected attempts never take that lock synchronously: they are offered to a bounded, non-blocking buffer that summarises identical attempts per actor, action and reason within 60 seconds into one record with a count, and a per-replica writer appends the buffered records in one chained transaction at most every second; overflow drops are counted in a metric. The table rejects `UPDATE` and `DELETE` through a database trigger. Each record is also emitted as a JSON `tracing` event with target `audit`.
Evidence: integration tests for atomicity, the trigger, the chain and the summarisation of rejected attempts; e2e scenarios that create, change and are refused, then read the records back; a load-test case that floods 403 responses while administrative writes are measured.

**FR-50 Access-decision log, write.** Every gateway decision produces one access record with the fields `decision_id` (UUID v7), `occurred_at`, `method`, `host`, `route_id`, `route_template`, `status`, `upstream`, `latency_us`, `bytes_in`, `bytes_out`, `request_id`, `subject_id`, `subject_kind`, `decision`, `reason`, `permission_key` or `denied`, `project_id`, `policy_version` and `credential_digest_prefix` (the first 8 hexadecimal characters of the credential digest). Records go through a bounded channel (`LOG_CHANNEL_CAPACITY`, default 65,536) to a dedicated writer thread, and each record goes to exactly one lane:
- the ordinary lane (allows sampled at `LOG_ALLOW_SAMPLE_RATE`, default 0.01, per-second aggregates and ordinary records) is written as JSON lines to stdout and shipped to Loki by Grafana Alloy; its delivery is best effort and losses are counted;
- the audit lane (every denial, every decision on an always-audit or sensitive key, every wildcard allow) is pushed directly to the Loki push API every `ACCESS_LOG_AUDIT_FLUSH_INTERVAL` (default 250 ms) and counts as delivered only once Loki acknowledges the push.
Per-class budgets per pod (`LOG_CLASS_BUDGETS`, default `error=1000,audit=2000` records per second) bound the volume; beyond a budget the writer emits one aggregate record per second per route, status and reason with a count. Audit or deny: a request on an always-audit or sensitive key gets 503 `audit_unavailable` when the audit lane is full or its oldest record is unacknowledged for longer than `ACCESS_LOG_AUDIT_MAX_PENDING` (default 2 seconds). Otherwise the decision is never delayed or changed, and every drop is counted per lane and class. No credential, cookie, GraphQL document or concrete path is ever written.
Evidence: integration tests for each lane rule, sampling, budgets and aggregates, audit-or-deny against a Loki container and a local HTTP stub that withholds acknowledgements, and non-blocking channel sends (`make.integration_tests`); a test with the template's log recorder that no field contains the credential.

**FR-51 Access-decision log, query.** REST `GET /api/access-decisions` and `GET /api/access-decisions/{id}`, and GraphQL `accessDecisions(...)` and `accessDecision(id)`, are served by `iam-control` from Loki through the `AccessLogQuery` port. A time range is required and may span at most `ACCESS_LOG_QUERY_MAX_RANGE` (default 24 hours, at most 7 days); a missing or longer range returns 422. Filters are subject id, subject kind, decision, reason, upstream, route id and status. Pages hold at most 500 entries, newest first, with an opaque cursor. Get by id derives the timestamp from the UUID v7 and searches a window of plus or minus 2 seconds; an absent id returns 404. A Loki query exceeding `ACCESS_LOG_QUERY_TIMEOUT` (default 30 seconds) returns 504 (GraphQL `extensions.code = QUERY_TIMEOUT`), never a partial page; Loki unavailable returns 503. The operations require `iam:audit:read`, and each query is itself audited.
Evidence: integration tests of the LogQL built for each filter, the range cap, the cursor, the get-by-id window and the timeout against a Loki container (`make.integration_tests`); e2e scenarios over both interfaces, including a range longer than the cap returning 422.

**FR-52 Security audit log, query and verification.** REST `GET /api/security-audit-events` (filters on time range, actor, action, target, outcome; cursor pagination) and `GET /api/security-audit-events/{id}`, and GraphQL `securityAuditEvents(...)` and `securityAuditEvent(id)`, require `iam:audit:read`. REST `GET /api/security-audit-events/chain-verification` (optional time range) and GraphQL `securityAuditChainVerification(...)` recompute the hash chain and return `valid` with the number of records checked, or `invalid` with the id of the first record that does not match. They accept optional `anchors` (a list of `{seq, hash}` previously published as `iam.security_audit.anchored` events and kept by an external audit pipeline) and report `invalid` when a recomputed head does not match an anchor, which detects a rewrite of the whole chain inside the database. Each query is itself audited.
Evidence: e2e scenarios over both interfaces; integration tests that tampering with a record (with the trigger disabled by the test) is reported at that record, and that a fully recomputed chain is reported against a mismatching anchor.

**FR-53 Log retention.** Access records are retained in Loki per stream, as set in the reference Loki configuration (FR-88): `lane="access"` for 90 days and `lane="audit"` for 400 days. IAM never deletes security audit records. IAM keeps no access-decision table in PostgreSQL and runs no partition maintenance.
Evidence: the Bats suite of FR-88 checks the retention per lane in the reference configuration (`make.bats`); the integration test of the audit trigger (FR-49).

### Health and configuration

**FR-54 Health probes.** `iam-control`'s `/api/health` reports the template's PostgreSQL probe plus two new dependencies: `kafka` (producer metadata reachable and the configuration gates of FR-72 passed) and `access-log-store` (the Loki ready endpoint answers). The overall status follows the template's rule. `/ping` keeps its template behaviour, and `service healthcheck` keeps it by default; `service healthcheck --mode gateway` probes `/ping` on `GATEWAY_PROBE_LISTEN` and is the gateway container's health check. The gateway serves `/internal/startup`, `/internal/ready` (FR-85), `/ping` and `/metrics` on its probe listener: startup passes after bootstrap, digest verification, the configuration gates and the first freshness proof attached to a published snapshot; liveness never depends on Kafka, PostgreSQL, Valkey or upstreams.

### Gateway configuration

**FR-56 Upstream management.** REST `POST /api/upstreams`, `GET /api/upstreams/{id}`, `GET /api/upstreams`, `PATCH /api/upstreams/{id}` and `DELETE /api/upstreams/{id}`, and GraphQL `createUpstream`, `upstream`, `upstreams`, `updateUpstream` and `deleteUpstream`, manage upstreams with `name` (service-name pattern of FR-30, unique among non-deleted upstreams), `namespace`, `service` (the Kubernetes Service), `catalogService` (the catalogue service whose keys authorize its routes), `forwardCredentials` (default false, FR-68), `port`, `protocol` (`http1` or `h2c`), `connectTimeoutMs`, `responseTimeoutMs`, `concurrencyLimit`, `retryBudgetPercent` and `outlierConsecutiveErrors`. A delete is refused with 409 while a route references the upstream. `RouteScopeGuard` applies (FR-4): a write on an upstream of catalogue service S needs `iam:route:{S}` or `iam:route:*`, and the seeded `system` upstream of service `iam` is refused with 409 `system_entry`. Each change is a versioned write with an `upstream/<name>` state record (FR-70) and an `iam.upstream.created`, `iam.upstream.updated` or `iam.upstream.deleted` event.
Evidence: e2e scenarios for create, read, list, update, delete, the referenced-delete conflict, the route-scope keys and the `system` refusal over both interfaces (`make.e2e_tests`); integration tests that each change writes its state record in the transaction (`make.integration_tests`); the contract-snapshot gate.

**FR-57 Route management.** REST `POST /api/routes`, `GET /api/routes/{id}`, `GET /api/routes` (filters host, upstream, service), `PATCH /api/routes/{id}` and `DELETE /api/routes/{id}`, and GraphQL `createRoute`, `route`, `routes`, `updateRoute` and `deleteRoute`, manage routes with `host`, `methods`, `pathPattern`, `service` (the catalogue service used for authorization), `upstream`, the flags `graphql`, `streaming` and `anonymous`, `enforcement` (`enforce` or `audit`), `bodyLimitBytes`, timeouts, `retryPolicy` (`none` or `idempotent`), `ratePolicyIds` and an optional `cors` policy (exact `https` origins, methods, headers, `allowCredentials`, `maxAgeSeconds` at most 86,400; FR-89). A route that overlaps another (same host and pattern with intersecting methods) returns 409. The write builds the host's candidate route table with the same `matchit` version and builder code the gateway uses, and refuses with 409 `route_table_conflict` any set the gateway could not build (for example `/users/{id}` next to `/users/{name}`). Precedence on a host is literal segments before parameter segments before catch-all segments, so a request matches at most one route per method. An anonymous route whose pattern is broader than a protected route on the same host returns 409. Routes of service `iam` and `system` routes are refused with 409 `system_entry`. Setting `anonymous = true` or `enforcement = audit` requires `iam:route:anonymous` (FR-4). Each change writes a `route/<id>` state record and an `iam.route.created`, `iam.route.updated` or `iam.route.deleted` event. An update that clears `anonymous`, moves `enforcement` from `audit` to `enforce`, or a deletion, is revocation-class (FR-75).
Evidence: e2e scenarios for each operation, the overlap conflict, the route-table conflict, the broader anonymous route, the service mismatch, the route-scope keys, the `system` refusal and the reserved-key guard over both interfaces; integration tests of the state record and of the default write mode for each revocation-class change.

**FR-58 Declarative route configuration.** REST `PUT /api/route-configurations/{host}` and GraphQL `applyRouteConfiguration` replace the full route set of one host atomically in one policy version; a set holds at most `ROUTE_CONFIGURATION_MAX_ROUTES` (1,000) routes and a larger set returns 422. With `dryRun = true` (REST query parameter, GraphQL input field) the operation returns the diff (added, changed and removed routes) without writing. REST `GET /api/route-configurations/{host}` and GraphQL `routeConfiguration(host)` return the current set. The guards of FR-57 apply per route, and the candidate route table is built for the whole set. A set whose diff deletes a route, clears `anonymous` or moves `enforcement` from `audit` to `enforce` is revocation-class (FR-75). The event `iam.route_configuration.applied` is recorded.
Evidence: e2e scenarios for apply, dry run, a guard violation and a route-table conflict that reject the whole set, and a set above the route limit returning 422, over both interfaces; unit tests of the revocation-class rule for diffs.

### Request path

**FR-59 REST proxy pipeline.** For each request on the public listener (`GATEWAY_LISTEN`), the gateway runs, in this order: header and connection limits (FR-67); the read-your-writes barrier (FR-14); one snapshot load and the freshness check (FR-73), with every later step using only that snapshot; route match on host, method and normalised path (404 when none); CORS preflight handling (FR-89); the local guard and rate limits (FR-65); authentication (FR-15, FR-17; 401 with `WWW-Authenticate: Bearer`), skipped only on anonymous routes (FR-63), followed by the CSRF rule for cookie-authenticated requests (FR-89); authorization with the route's catalogue keys (403 with a reason code that never discloses whether an operation exists in another service); header rewrite (FR-68); forwarding (FR-66, FR-87); unbuffered relay of the response; and the access record (FR-50). The pipeline answers with the statuses 400, 401, 403, 404, 405, 413, 415, 429, 431, 502, 503 and 504 for its own outcomes, and 500 for a caught panic. IAM's own management routes pass through the same pipeline before they reach `iam-control`.
Evidence: integration tests of the step order with fakes, asserting one snapshot load per request and the barrier before the load (`make.integration_tests`); e2e scenarios through the gateway in the compose world for each status the pipeline produces (`make.e2e_tests`); unit tests that reason codes do not disclose other services.

**FR-60 GraphQL proxying.** On routes flagged `graphql`, the gateway buffers the body up to the route limit (64 KiB default, 6 MiB on IAM's own GraphQL route) and returns 413 above it; accepts `POST` only (405 with `Allow: POST` otherwise, so an operation never travels in a URL); accepts `application/json` only, and multipart and other content types return 415; rejects JSON with duplicate keys; accepts only the envelope members `query`, `operationName`, `variables` and `extensions`, requires a non-empty `query` string, and rejects `extensions.persistedQuery` and any document-id member (`documentId`, `queryId`, `id`) with 400; treats an empty coordinate set as `malformed_operation`, a denial; accepts batch arrays of at most 10 operations and authorizes each one; extracts coordinates per FR-8 with the document cache; enforces a per-subject parse budget of 20 document-cache misses per second and 1 MB of parsed text per second (CONFIG), returning 429 above it; parses documents above 8 KB through `spawn_blocking` on the bounded blocking pool, never on a request worker; allows introspection only with `gql:{service}:__introspection`; and forwards the original bytes unchanged.
Evidence: integration tests for each limit, duplicate keys, the envelope rules, `GET` and multipart refusals, batches, introspection, the parse budget and the off-worker parse of large documents (`make.integration_tests`); an e2e scenario that uploads a 5 MiB SDL through the gateway over REST and over GraphQL (`make.e2e_tests`); the parser-differential corpus of NFR-40.

Epic 1 slice (FR-60): A benchmark in `crates/service/benches/` parses a representative corpus of GraphQL documents of 1, 5, 8 and 64 KiB with the `async-graphql` parser and reports the parse cost per document size, recorded as measured on the named host with its CPU model and never as a gate value. The result is the first measured reference for the decision, in a later epic, to parse documents above 8 KB off the request workers.
Evidence: `make.bench_spikes` reports a median and a p99 per document size; `make.docs_check` passes with `docs/spikes/phase-0.md` listing the CPU model and labelling every figure as a host measurement (Story 1.6).

### Streams and subscriptions

**FR-61 WebSocket and SSE streams.** On routes flagged `streaming`, the gateway authorizes the opening request (WebSocket upgrade or SSE request) and registers the stream in a registry indexed by subject and session. When a policy version is applied, the gateway re-evaluates the streams that version affects and closes the revoked ones (WebSocket close 1008, SSE stream ended) before the version is reported applied to Sync-Fence (FR-76). Each stream is registered with the earliest expiry of the assignments that authorized it, because an assignment expiry produces no policy version; at that instant the stream is decided again on the current snapshot and closed when denied. Every stream closes at `min(token exp, STREAM_MAX_LIFETIME)` (default 1 hour) and after `STREAM_IDLE_TIMEOUT` (default 60 seconds) without traffic. A request without a token is refused with 401 before any upgrade, except on routes flagged `graphql` and `streaming`, where FR-62 authenticates through `connection_init` before any upstream connection exists. Each stream is registered with the snapshot version that authorized it; a stream registered below the published version or below the finished-re-evaluation mark is re-checked at once, and the mark for V advances only when no stream registered below V remains unevaluated. When the published snapshot's proof age exceeds `FRESHNESS_HARD_BOUND`, or the pod fences or goes unready for staleness, the gateway closes every registered stream and subscription (WebSocket 1013, SSE stream ended), because GOAWAY never reaches upgraded connections. Stream routes have no compression and no response timeout.
Evidence: integration tests with a fake upstream for WebSocket and SSE in which a revocation closes the stream before the version is reported applied, a stream opened while V is applied is evaluated against V, a pod cut off from Kafka closes its streams within `FRESHNESS_HARD_BOUND`, a stream authorized only by an expiring assignment closes at that expiry, and with paused time for the lifetime and idle limits (`make.integration_tests`); an e2e scenario of a stream closed by a role revocation.

**FR-62 GraphQL subscriptions.** Routes flagged `graphql` and `streaming` accept the WebSocket subprotocols `graphql-transport-ws` and `graphql-ws` only; any other subprotocol is refused with 400 before the upgrade. The gateway decodes frames in both directions. The gateway completes the client-side handshake itself and opens no upstream connection before authentication: it reads `connection_init` within `GRAPHQL_WS_INIT_TIMEOUT` (default 5 seconds; silence closes with 4408), takes the token from the upgrade request or, when absent there, from the `connection_init` payload field `authorization`, verifies it (a missing or invalid token closes the socket with 4401) and authorizes the route on the authenticated principal (a denial closes with 4403). Only then does it open the upstream WebSocket and forward a `connection_init` whose payload has `authorization` removed unless the upstream has `forwardCredentials = true` (FR-68), relay the upstream's `connection_ack` and register the connection. Each `subscribe` or `start` message, and each query or mutation sent over the socket, is authorized per coordinate before it is forwarded; a denial answers that operation id with an `error` message carrying `extensions.code = FORBIDDEN`, and the socket stays open. A connection holds at most `GRAPHQL_WS_MAX_SUBSCRIPTIONS` (default 100) operations, and messages are at most 64 KiB. Each open operation is stored with the earliest expiry of its authorizing assignments and decided again at that instant. When an applied version or that expiry denies an open operation, the gateway sends `complete` upstream and `error` downstream; a session revocation or cut-off closes the socket with 4403; a malformed frame closes it with 4400. A `subscribe` or `start` payload follows the envelope rules of FR-60; one with `extensions.persistedQuery`, a document-id member or no non-empty `query` is answered with an `error` for its id. The staleness rule of FR-61 closes subscriptions too. GraphQL over SSE is accepted in distinct-connections mode only, authorized when the stream opens like any GraphQL request; the single-connection mode's `PUT` reservation returns 405.
Evidence: integration tests for both subprotocols, the `connection_init` token (no upstream connection exists before authentication, and the forwarded payload carries no token for an upstream without `forwardCredentials`), assignment expiry of an open operation, each close code, the per-operation `FORBIDDEN` answer, the subscription cap and re-evaluation on change (`make.integration_tests`); an e2e scenario of a subscription refused and of one completed after a role revocation.

### Route behaviour, rate limits and upstreams

**FR-63 Anonymous routes.** Routes flagged `anonymous` skip authentication and authorization but keep rate limits, body limits and freshness fencing: a pod whose snapshot has no valid freshness proof answers 503 on anonymous routes too. The reference route configuration flags User service's public endpoints (sign-in, two-factor sign-in, token, OAuth, password reset, user registration, user confirmation and health).

**FR-64 Rate-policy management.** REST `POST /api/rate-policies`, `GET /api/rate-policies/{id}`, `GET /api/rate-policies`, `PATCH /api/rate-policies/{id}` and `DELETE /api/rate-policies/{id}`, and GraphQL `createRatePolicy`, `ratePolicy`, `ratePolicies`, `updateRatePolicy` and `deleteRatePolicy`, manage rate policies with `name`, `key` (`ip`, `subject`, `subject_route` or `route`), `limit`, `periodMs`, `burst` and `fallback` (`divided` or `full`). A delete is refused with 409 while a route references the policy. Each change writes a `ratepolicy/<id>` state record and an `iam.rate_policy.created`, `iam.rate_policy.updated` or `iam.rate_policy.deleted` event.

**FR-65 Rate-limit enforcement with Valkey.** A local per-IP guard always runs first. Routes that carry rate policies are then checked exactly and globally in Valkey through the `RateLimitStore` port: one atomic GCRA Lua script call per policy and request, under the key `rl:{policyId}:{keyHash}` (key parts hashed). Over the limit the gateway answers 429 `rate_limited` with `Retry-After`. Each call is bounded by `RATE_LIMIT_STORE_TIMEOUT` (default 5 ms). After 5 consecutive failures or timeouts a breaker opens for `RATE_LIMIT_BREAKER_OPEN_DURATION` (default 5 seconds) and then lets one probe through. While the breaker is open, or for a single timed-out call, a conservative local limiter decides: `limit / N_ready` per pod, where `N_ready` is the number of ready gateway pods (at least 1), or the full limit per pod for policies with `fallback = full`. The limiter never returns 503 and never changes an authorization decision. Routes without a rate policy never call Valkey, and Valkey holds counters only.
Evidence: unit tests of the GCRA rule (`make.unit_tests`); integration tests against a Valkey container for exact counting across two gateway instances, the timeout, the breaker and both fallback modes (`make.integration_tests`).

**FR-66 Upstream resilience.** Upstream timeouts are: connect 250 ms, response headers 10 seconds for REST and 30 seconds for GraphQL, whole request 60 seconds, and none for streams (CONFIG, overridable per route and upstream). A request is retried only when it provably was not sent (the forwarder resends the request hyper hands back), or when its method is idempotent on a route with `retryPolicy = idempotent` and it has no body or a body buffered under 64 KiB (CONFIG), because a streamed body is consumed by the first attempt; at most one retry, to another endpoint, within a retry budget of 10% per upstream; GraphQL mutations are never retried. Outlier ejection removes an endpoint after 5 consecutive connect errors or 5xx responses for 10 seconds, ejecting at most 50% of endpoints. A per-upstream concurrency limit fails fast with 503 `upstream_overloaded`. Upstream failures return 502, and upstream timeouts return 504.
Evidence: integration tests with a fake upstream for each timeout, each retry rule (including no retry of a mutation and no idempotent retry of a streamed body above the buffer cap), the retry budget, outlier ejection and the concurrency limit (`make.integration_tests`).

**FR-67 Edge TLS and protocol hardening.** The gateway terminates TLS 1.3 and 1.2 in the pod with the certificate in `GATEWAY_TLS_CERT_FILE` and `GATEWAY_TLS_KEY_FILE`, reloaded when the files change, with ALPN `h2` and `http/1.1`. When `GATEWAY_PROXY_PROTOCOL` is true, it reads the client address from Proxy Protocol v2. Limits: header block at most 16 KiB (431 above it); header read timeout 10 seconds; HTTP/2 `max_concurrent_streams` 128 and `max_header_list_size` 16 KiB; buffered bytes at most 256 KiB per connection and 256 MB per pod; at most 64 connections per client IP and 32 per subject; keep-alive idle 120 seconds; connection age capped at 10 minutes plus or minus 20%, ended with GOAWAY. Conflicting `Content-Length` and `Transfer-Encoding` headers are rejected, hop-by-hop headers are stripped, and the HTTP/2 `:path` is validated. All limits are CONFIG.
Evidence: integration tests for certificate reload, Proxy Protocol parsing, each limit and each rejected framing case (`make.integration_tests`); the smuggling suite of NFR-40.

**FR-68 Principal propagation.** The gateway strips every client-supplied `X-IAM-*`, `Forwarded` and `X-Forwarded-*` header, then sets `X-IAM-Subject`, `X-IAM-Subject-Kind`, `X-IAM-Session`, `X-IAM-Policy-Version`, `X-Request-Id` and `X-Forwarded-For` on the upstream request. It forwards `Authorization` and the `__Host-auth_token` cookie unchanged only to upstreams with `forwardCredentials = true` (User service, whose routes re-check sessions, and `iam-control`), and strips both from every other upstream request, which relies on the `X-IAM-*` headers. It adds `X-IAM-Policy-Version` to every response.

**FR-69 Per-route enforcement mode.** A route's `enforcement` is `enforce` by default. In `audit` mode the gateway logs a would-deny decision with reason `audit_mode_would_deny` and forwards the request. Changing the mode requires `iam:route:anonymous` and is audited.

### Policy replication and freshness

**FR-70 Policy state publication.** Every versioned transaction locks the counter row of `iam_policy_epoch`, increments the gap-free policy version, writes one state row per changed entity (keys `role/<uuid>`, `subject/<kind>/<id>`, `catalog/<service>/manifest`, `catalog/<service>/<catVer>/<chunk>`, `route/<id>`, `upstream/<name>`, `ratepolicy/<id>`, `revocation/session/<sid>`, `revocation/user/<uid>`, `revocation/global`) carrying the full new state as JSON with `schemaVersion`, or a tombstone for a deleted entity, updates the 128-bit XOR digest computed in Rust from the SHA-256 hash of each entity, and writes a `__head` row `{version, digest}`. State rows carry the framing headers `iam-version`, `iam-seq`, `iam-count`, `iam-digest-after`, `iam-op`, `iam-schema`, `iam-log-epoch` and `iam-relay-epoch`. Catalogues are written as content-addressed chunks of at most 1 MiB plus a manifest. Transactions that do not change decisions write event rows only.
Evidence: integration tests that each versioned write produces its state rows and `__head` in its transaction, that a large catalogue is chunked and that unchanged chunks are not rewritten (`make.integration_tests`); a property test that the PostgreSQL digest equals a digest replayed from the state rows.

**FR-71 Gateway policy consumer, bootstrap and apply.** Each gateway pod reads `POLICY_TOPIC` without a consumer group: it assigns partition 0, reads with `read_committed`, and keeps its position in memory. Bootstrap reads from offset 0 to the high watermark captured at start (`HW0`) under the principal `iam-gateway-bootstrap`; PostgreSQL never takes part. Versions are assembled from `iam-seq` and `iam-count` and applied only when complete and contiguous. Duplicates are ignored when their `iam-digest-after` matches a ring of the last 100,000 versions. Conflicting content for one version, a lower log epoch, a gap, a record whose broker append time is older than 1 hour in tail mode, or a watermark regression fences the pod: it keeps its last verified snapshot until `FRESHNESS_HARD_BOUND` and rebootstraps after a random delay of up to `FRESHNESS_READY_BOUND`. Apply runs on a dedicated thread into 4,096 copy-on-write shards and publishes at most once per 5 ms (CONFIG); replaced snapshots are freed on the apply thread. The digest is checked after each version and before that version is published: a version whose digest does not match is never published, and the pod fences as above on its last verified snapshot. With the transactional relay, `HW0` and every probe use `ListOffsets` with isolation `READ_COMMITTED`, so they stop at the last stable offset.
Evidence: integration tests against the compose broker and krafka's `test-broker` for bootstrap, an incomplete trailing version, duplicates, each fencing cause and the staggered rebootstrap (`make.integration_tests`); the property test of NFR-16 that incremental apply equals a full rebuild.

**FR-73 Freshness proof and staleness bound.** Every `FRESHNESS_PROBE_INTERVAL` (default 500 ms) the pod records `t_s` on the `BootClock` (`CLOCK_BOOTTIME`) before sending anything, confirms the partition leader and leader epoch with at least 2 of the 3 replica brokers, and sends `ListOffsets` with `current_leader_epoch` for every partition of the topic. A leader-epoch error, an unavailable offset, a regressed watermark or a nonzero watermark on another partition yields no proof. The proof is attached to the published snapshot once that snapshot contains every complete version below `HW(t_s)`. The pod allows a request only while `now - last_proof` is at most `FRESHNESS_HARD_BOUND` (15 seconds now, 5 seconds as the target) and a 1-second watchdog shows no gap above `FRESHNESS_READY_BOUND` (2 seconds) since that proof. If a peer reports a newer applied version for more than 1 second while the pod's proof says fresh, the pod treats its proof as invalid. Otherwise the pod answers 503 `iam_stale` with `Retry-After: 1`.
Evidence: paused-time integration tests that allows stop exactly at the bound, that a watchdog gap invalidates the proof, that each probe error yields no proof (through krafka's `test-broker`) and that the peer cross-check works (`make.integration_tests`); broker-failover and zombie-leader tests T14 and T15 in story 16.8, outside `make ci`.

**FR-74 Derived-state check.** Every `DERIVED_STATE_CHECK_INTERVAL` (default 60 seconds) the apply thread rebuilds the derived structures (compiled role sets, reverse indexes, interned assignment lists, routers) of a rotating 1/16 of the shards from the raw records and compares a hash of the decision-relevant output with the incremental structures. A mismatch means the published snapshot is wrong, so the pod stops allowing at once: every request gets 503 `iam_stale` (decision API `deny` with reason `unavailable`), the pod fails readiness, and it rebootstraps after the random delay of FR-71. It does not keep serving the corrupt snapshot until `FRESHNESS_HARD_BOUND`. Pods export `applied_version`, `digest` and `derived_hash` as metrics.
Evidence: an integration test that corrupts a derived structure and asserts that no request is allowed from the moment the mismatch is detected, that the pod fences and that the metrics change (`make.integration_tests`).

**FR-75 Write modes.** Every management write runs in one of two modes, from one handler result mapped to both interfaces:
- `published` (default): the write returns after the PostgreSQL commit and the point at which its version's `__head` record is visible to `read_committed` readers (the Kafka acknowledgement with the idempotent relay, the completed transaction commit with the transactional relay), with `Iam-Policy-Version` and `Iam-Policy-Offset`; if the acknowledgement takes longer than `PUBLISH_WAIT_TIMEOUT` (default 2 seconds), it returns 202 with status `committed_pending_propagation`;
- `propagated` (REST `Prefer: wait=propagated`, GraphQL input `consistency: PROPAGATED`): the write also waits for Sync-Fence (FR-76) and returns `Iam-Propagation: complete` or `bounded` with the counts of pods that acknowledged and pods that timed out.
GraphQL payloads carry `propagation {status, policyVersion, podsAcknowledged, podsTimedOut}`. Revocation-class writes run in `propagated` mode by default: delete role (FR-23); a grant replacement that removes at least one key (FR-24); revoke assignment (FR-29); an activation or retirement that orphans grants (FR-32, FR-36, FR-38); an assignment expiry shortened or newly set (FR-28); a route update that clears `anonymous`, moves `enforcement` from `audit` to `enforce`, or deletes the route (FR-57); an applied route configuration whose diff does any of these (FR-58); revoke sessions and set cut-offs (FR-80). A revocation-class change above `BULK_CHUNK_ENTITIES` runs as a bulk operation whose revoke-type chunks are each fenced before the next chunk commits (FR-84). Revocations consumed from `user.events.v1` are fenced asynchronously (FR-18).
Evidence: e2e scenarios for each mode and for the 202 answer over both interfaces (`make.e2e_tests`); integration tests that each revocation-class write defaults to `propagated` (`make.integration_tests`).

**FR-76 Sync-Fence coordinator.** For a write in `propagated` mode, `iam-control` lists gateway pods by `GATEWAY_FLEET_LABEL` with a consistent read, counts pods with no started container and pods whose gateway container has terminated as complete, and long-polls `GET /internal/policy/applied?atLeast=V&offset=O&wait=T` (O is the write's offset) on the others, on the gateway's internal listener, which admits only `iam-control` and gateway pods. A pod answers after it has published version V and no stream registered below V remains unevaluated; a bootstrapping pod answers at once when its `HW0` lies beyond O; when the wait (capped at `FRESHNESS_HARD_BOUND` plus 1 second) ends, it answers 204 without an acknowledgement; at most `APPLIED_POLL_MAX_CONCURRENT` (256) polls wait at once and a further poll gets 503. Every answer, and `/internal/freshness`, carries the pod's configured `FRESHNESS_HARD_BOUND` as `hardBoundMs`. Concurrent writes are batched into one long poll per pod. The coordinator returns `complete` when every polled pod answered, or `bounded` after `max(own FRESHNESS_HARD_BOUND, the highest hardBoundMs any gateway pod reported in the last 24 hours) + SYNC_FENCE_MARGIN` (default 0.5 seconds), so a fleet in the middle of a `T_hard` change never receives an early `bounded`. Pods are listed through the `PodLister` port with a Kubernetes adapter and a static-list adapter.
Evidence: integration tests with the static adapter and fake pods for non-started and terminated pods, the bounded answer at exactly the bound, mismatched hard bounds across pods, batching, the concurrency cap and a bootstrapping pod (`make.integration_tests`); tests of the Kubernetes adapter against a fake Kubernetes API.

**FR-77 Anti-entropy and relay repair.** A singleton checks the topic's newest `__head` against PostgreSQL every `ANTI_ENTROPY_HEAD_INTERVAL` (default 10 seconds) and runs a full check every `ANTI_ENTROPY_FULL_INTERVAL` (default 5 minutes): it verifies that stored published offsets still hold the expected versions, republishes lost records as a repair, checks for each key written since the previous head check that the key's last record by offset carries its newest PostgreSQL version and republishes the current state when it is lower (within the 1-hour `min.compaction.lag.ms`, so compaction never keeps a stale value from a zombie relay), and runs a shadow bootstrap that compares the full digest with PostgreSQL. A mismatch raises an alert within 10 seconds.
Evidence: integration tests against the compose broker that a deleted or overwritten record is republished, that a lower-version record appended after a takeover republish is superseded within one head interval, that a head mismatch alerts within the interval, and that the shadow bootstrap compares the full digest (`make.integration_tests`).

**FR-78 Policy resync.** REST `POST /api/policy-resyncs` and GraphQL `resyncPolicy` (requires `iam:policy:resync` and a `reason`) republish the full current state as a new log epoch, with versions continuing above the topic's maximum, as a bulk operation (FR-84). The resync is audited and records `iam.policy.resynced`. It replaces the operator cache flush of the superseded design.
Evidence: e2e scenarios over both interfaces (`make.e2e_tests`); an integration test that gateway pods converge on the new log epoch with a digest equal to PostgreSQL's (`make.integration_tests`).

**FR-79 Revocation tombstones.** The control-plane emitter tombstones a session-revocation or user cut-off record only after its `prune_after` instant: the record's cut-off instant plus the longest `MAX_TOKEN_LIFETIME` ever configured plus twice the largest allowed `JWT_CLOCK_SKEW` (2 × 60 seconds) plus a 60-second margin. The cut-off instant is the later of `revoked_at` and the instant the record refuses tokens up to: `tokens_valid_after` for a user cut-off, and `occurredAt` plus `JWT_CLOCK_SKEW` for a session revocation taken from a User service event. A refused token can be issued up to the cut-off instant, lives at most `MAX_TOKEN_LIFETIME`, and is accepted until its `exp` plus the skew, so the tombstone never makes a still-acceptable token valid again, even when User service clocks run ahead of IAM's; that longest value is kept in the single-row table `iam_token_lifetime_floor` and raised at startup when the configured value is higher. Gateway pods never prune revocation state by clock.
Evidence: integration tests with a controlled `Clock` that no tombstone is written before the bound and one is written after it, and that raising `MAX_TOKEN_LIFETIME` never shortens retention of existing records (`make.integration_tests`).

### Kubernetes operations

**FR-85 AZ-aware peer-relative readiness.** Every 2 seconds each gateway pod compares its freshness with its peers: all peers while the fleet has fewer than 10 pods, otherwise 5 peers with 3 in its own availability zone. When the pod is stale but most peers are fresh, after 2 consecutive verdicts it fails readiness and sends HTTP/2 GOAWAY or `Connection: close` on the next HTTP/1.1 response; it becomes ready again after 3 consecutive fresh verdicts. The last `READINESS_AZ_FLOOR` (default 1) ready pods of a zone never go unready for staleness. When staleness is fleet-wide, pods stay ready and fail closed per request.

**FR-86 Graceful drain.** The preStop hook is an `exec` of `service drain`, a subcommand of the same binary, which calls `GET /internal/drain` on the probe listener over loopback; the endpoint answers only loopback peers (403 otherwise), so no other pod can drain the gateway. ### Edge policy and service-to-service calls

**FR-89 CORS and CSRF at the gateway.** A route may carry a `cors` policy (FR-57). The gateway answers a preflight (`OPTIONS` with `Origin` and `Access-Control-Request-Method`) after the route match and before authentication: 204 with the allowed methods, headers, `Access-Control-Allow-Credentials` and `Access-Control-Max-Age` when the origin and method are allowed, otherwise 403 `cors_rejected`; a route without a policy refuses every preflight. Responses to an allowed origin carry `Access-Control-Allow-Origin` with that exact origin, never `*` together with credentials, and `Vary: Origin`. A request with an unsafe method (`POST`, `PUT`, `PATCH`, `DELETE`) or a WebSocket upgrade that is authenticated by the `__Host-auth_token` cookie needs an `Origin`, or a `Referer` when `Origin` is absent, equal to the request's own origin or listed in the route's allowed origins; otherwise it gets 403 `csrf_rejected`. Requests authenticated by an `Authorization: Bearer` header are exempt. The rule depends on User service setting `SameSite` on the cookie, which `docs/operations.md` records.
Evidence: unit tests of the CORS and CSRF rules (`make.unit_tests`); integration tests for preflights, response headers, each `Origin` case and a cross-site WebSocket upgrade (`make.integration_tests`); an e2e scenario of a cookie-authenticated management write from the CRM origin (`make.e2e_tests`).

**FR-90 East-west calls through the gateway.** Calls between VilnaCRM services go through the gateway's east-west listener `GATEWAY_MESH_LISTEN` (TLS with the same certificate, no Proxy Protocol, client address from the TCP peer), reached through the ClusterIP Service `iam-gateway-mesh`. It runs the same pipeline and route table as the public listener; callers authenticate with `ROLE_SERVICE` tokens carrying the caller audience of FR-3, or forward the user's token when they act for that user. Upstream namespaces admit ingress only from gateway pods (FR-88), so a direct call between services is refused and an upstream can trust `X-IAM-*` headers.
Evidence: integration tests in which a service token reaches an upstream through the east-west listener with `X-IAM-Subject-Kind: service`, a forged principal header never arrives, and a Proxy Protocol header is refused (`make.integration_tests`); the NetworkPolicy invariants in the Bats suite (`make.bats`).

### Performance and capacity

**NFR-33 Gateway residence latency.** Gateway residence time is the time a request spends inside the gateway, measured server side (accept to upstream write, plus upstream first byte to last client byte). Targets, unmeasured: warm REST on the hottest pod at no more than 60% CPU, p95 at most 0.5 ms and p99 at most 1 ms; warm GraphQL with a document-cache hit at most 0.1 ms above REST; a token the pod has not seen before, residence p99 at most 1.2 ms; routes with a Valkey rate policy, p99 at most 2 ms; end-to-end added latency p99 at most 2 ms with zone-aware routing. For orientation, the design's ESTIMATE for warm REST residence is p50 0.09 ms, p95 0.20 ms and p99 0.45 ms (conservative 0.25, 0.6 and 1.2 ms). The gateway-to-upstream round trip is reported separately. Gate: the benchmark story 16.7 on EKS reference nodes, outside `make ci`, with stored HdrHistogram artefacts; CI microbenchmarks are trend reports, not gates. If the benchmark misses a target, the hyper pipeline is profiled and optimised before release.

Epic 1 slice (NFR-33): The RS256 verify and GraphQL parse benchmarks of FR-15 and FR-60 give the first measured reference for the latency estimates: each figure is recorded in `docs/spikes/phase-0.md` with the CPU model as measured on that host, and the residence-latency figures of the master plan stay targets, not gate values. Evidence: `make.bench_spikes` (outside `make ci`) and `make.docs_check` (Story 1.6).

**NFR-34 First-release capacity.** The first release is sized for the decided peak of 1,000 requests per second. The first-release fleet is 6 gateway pods, 2 per availability zone across 3 zones, each requesting 1 CPU with no CPU limit and 2 GiB of memory (request equals limit) and running `TOKIO_WORKER_THREADS=2`; the HPA keeps 6 to 9 pods at a 50% CPU target (all CONFIG). At peak each pod serves about 170 requests per second (ESTIMATE); the fleet size is set by zone availability, not by load. Targets: the first-release fleet sustains 2,000 requests per second (twice the decided peak) with zero gateway-caused 5xx responses at the latencies of NFR-33; a per-pod saturation run on the production protocol mix sustains at least 5,000 planned requests per second per worker vCPU at 50% CPU (ESTIMATE 6,250 expected, 2,500 conservative), with the saturation knee at least 1.6 times that planned rate (8,000 requests per second per worker vCPU, test T1). Gate: tests T1 and T2 in the benchmark story 16.7, outside `make ci`; the k6 smoke variants in `make.smoke_load_tests` check correctness only.

**NFR-37 Bootstrap to fresh.** Target: a single joining pod becomes fresh (bootstrap complete, digest verified, first proof attached) within 30 seconds at the first-release data size and at 1 million users (ESTIMATE 3 to 20 seconds). The startup probe allows 300 seconds (CONFIG). Gate: test T8 in story 16.7, outside `make ci`.

Epic 1 slice (NFR-37): A reader without a consumer group reads a 200 MB topic on the compose broker from offset 0 with a documented command run outside `make ci`, and the read rate is recorded in `docs/spikes/phase-0.md` as a compose-host measurement next to the 100 MB/s target, never as a gate value. Evidence: `make.docs_check` (Story 1.5).

**NFR-38 Snapshot memory.** The steady policy snapshot uses at most 12.5% of the pod memory request: 256 MB at 2 GiB (ESTIMATE 30 to 60 MB at 100,000 users and 170 to 220 MB at 1 million users). Gate: test T13 in story 16.7, outside `make ci`.

**NFR-39 No CPU throttling.** Gateway manifests set no CPU limit, and the benchmark configuration shows zero CFS-throttled periods. Gates: the Bats suite of FR-88 (`make.bats`) and the benchmark story 16.7.

**NFR-43 Zone locality.** At steady state at most 5% of upstream requests cross availability zones while the gateway pod's own zone has healthy endpoints (target). Gates: property tests of the zone-aware selection with a seeded `Rng` (`make.unit_tests`) and test T24 in story 16.7.

### Freshness and propagation

**NFR-19 Session revocation freshness.** From the Kafka acknowledgement of a User service event on `user.events.v1` to its enforcement on every healthy gateway pod: target p99 at most 1 second (ESTIMATE 0.2 to 0.5 seconds). Consumer lag raises an alert at 2 seconds and a page at 10 seconds. Time before the event's acknowledgement (User service not publishing) and consumer stalls are not bounded by this target; the absolute backstop is `MAX_TOKEN_LIFETIME` (900 seconds), after which every access token of a revoked session has expired. Gates: integration tests with a controlled `Clock` against the compose broker (`make.integration_tests`); test T32 in story 16.8, outside `make ci`.

**NFR-35 Policy propagation.** Targets on the first-release fleet: PostgreSQL commit to applied on every healthy gateway pod p99 at most 500 ms (ESTIMATE 150 to 300 ms); a Sync-Fence write p99 at most 1 second with no pod in transition (ESTIMATE 300 ms). A write whose pods do not all answer returns `bounded` after `FRESHNESS_HARD_BOUND` plus `SYNC_FENCE_MARGIN` (15.5 seconds now, CONFIG). Gates: tests T6 and T7 in story 16.7 and T19 in story 16.8, outside `make ci`; ordering and correctness through the integration tests of FR-71 and FR-76.

**NFR-36 Enforced staleness bound.** No gateway pod allows a request on a snapshot whose freshness proof is older than `FRESHNESS_HARD_BOUND`: 15 seconds now, tightened to the 5-second target only after the broker-failover test T14 shows a proof gap of at most 2 seconds. The bound is conditional on the Kafka configuration gates (FR-72), relay fencing (FR-46) and the replica-quorum epoch check, which phase-0 spike story 1.3 and test T15 must confirm; until then it is labelled conditional. Gates: paused-time integration tests of FR-73 (`make.integration_tests`); tests T14 and T15 in story 16.8, outside `make ci`.

Epic 1 slice (NFR-36): The freshness bound stays labelled conditional; Epic 1 supplies the spike evidence it is conditional on: the leader-epoch and `ListOffsets` capabilities of FR-73 and the configuration reads of FR-72 pass or are recorded as failed, and the replica-quorum observations on the 3-broker compose profile are recorded as compose-host measurements. ### Assumptions

The assumptions that shape these requirements are recorded as `> Assumption:` lines in `research.md`. The ones that change observable behaviour are restated here.

> Assumption: A valid validate-access request always returns HTTP 200 with a decision body, including `deny` with reason `unavailable` when IAM cannot decide; callers treat timeouts and non-200 responses as denials.

> Assumption: The first release supports global and project scopes only, because no tenant identifier exists in User service tokens or Core service today.

> Assumption: GraphQL decisions are all-or-nothing; partial responses are out of scope.

> Assumption: OpenAPI documents are uploaded as JSON only.

> Assumption: IAM's administrative API is protected by IAM's own catalogue keys, generated from IAM's own contracts and registered at startup, plus the reserved `iam:` keys; the first administrator is created by `service iam-bootstrap`.

> Assumption: Latency, capacity, propagation and freshness figures are targets or estimates; they become gates through the benchmark stories 16.7 and 16.8 on EKS reference nodes, outside `make ci`, and are never set looser than stated here. `make ci` runs only the k6 smoke variants and microbenchmark trend reports.

> Assumption: Anonymous routes are fenced on staleness like every other route, so a Kafka outage longer than `FRESHNESS_HARD_BOUND` also blocks sign-in and token refresh (open owner decision D5, default kept).

> Assumption: The first-release fleet is 6 gateway pods, 2 per zone across 3 zones, each requesting 1 CPU with no limit, 2 GiB of memory and 2 tokio workers, with an HPA between 6 and 9 pods at 50% CPU; two pods per zone are needed because NLB cross-zone balancing is off.

> Assumption: Only first-party access tokens with a lifetime of at most 900 seconds pass the gateway (open owner decision D12, default kept); up to three public keys are read from a file and tried newest first until User service adds `kid` and a JWKS endpoint (D11).

> Assumption: Each upstream service has its own public host, and the gateway speaks HTTP/1.1 to PHP upstreams until h2c is verified (open owner decision D10, default kept).

> Assumption: Valkey runs in the cluster as one primary and two replicas with Sentinel, one node per zone; Amazon ElastiCache for Valkey remains a configuration change behind the same port (D23).

> Assumption: Loki runs in simple scalable mode on EKS with S3 object storage and replication factor 3, fed by a Grafana Alloy DaemonSet; retention is 90 days for the `access` lane and 400 days for the `audit` lane, and audit-or-deny applies to always-audit and sensitive keys only (D24, D26).

> Assumption: The User service topic is `user.events.v1`, keyed by user id, with the neutral envelope carrying the event id, `occurredAt`, `userId` and, for session events, `sessionId`; the name and payload are to be agreed with the User service team (D25).

> Assumption: `KAFKA_CONFIG_GATES=relaxed` is used only in `dev` and `test`, where docker compose runs a single KRaft broker.

## API Surface Summary

Every row is one capability, one handler in `iam-application` and two interfaces (FR-1). All REST paths are under `/api` on `iam-control`, reached through the gateway on IAM's host; GraphQL is served at `POST /api/graphql`. Every operation needs a bearer token (FR-3) and the rule of FR-4. The decision API rows (validate, batch, resolve token) are also served by `iam-gateway` on its decision listener (`GATEWAY_DECISION_LISTEN`, port 9091) at the same paths, including a GraphQL endpoint at `/api/graphql` that exposes only those three queries; the published contract snapshots are generated from the `iam-control` router. Every write accepts the write-mode modifier of FR-75 (REST header `Prefer: wait=propagated`, GraphQL input field `consistency: PUBLISHED | PROPAGATED`), and every write response carries `Iam-Policy-Version` (REST) or `propagation` (GraphQL payload). The operator cache flush of the superseded design is removed; policy resync replaces it.
